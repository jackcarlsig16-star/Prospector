SPEC — sales-pipeline-v1

## Status
Source: Jack in chat, 2026-09-30. Seif's weekly sales report needs pipeline data (sections 6
Pipeline, 7 Pipeline Movement, 8 Top Opportunities, 12 Forecast). Six of the eleven scorecard
rows also depend on it. None of this exists in the repo. sales-analytics-dashboard-v2 (shipped,
Stages 1–5, last commit 2762584) covers Apollo email and sequence data only.
This SPEC is the foundation for sales-analytics-scorecard-v1 and sales-weekly-report-v1. Ship it
first.
Pipeline data is NOT in Apollo. Today it lives in a manual Google Sheet that Jack and Cyrus
(freelance sales) maintain, so the source is manual entry plus CSV import.

## Problem
1. There is no place in Prospector to record an opportunity (organization, covered lives, stage,
   next step, close date), so pipeline totals, movement and the forecast can't be computed.
2. Funnel stages aren't standardized, so "what moved forward / back / stalled" can't be
   determined.

## Design decision

DECIDED
- Tenant-scoped (HomeLover), with RLS and tenant guards identical to the existing sales_* tables
  and api/sales/routes.js. HumanKind must get 403 or 0 rows.
- Canonical stage enum, used by every later SPEC:
    target → contacted → responded → meeting → proposal_pilot → verbal → contract → launched,
    plus terminal 'lost'.
  Stage order is defined ONCE in a shared constant (alongside the existing salesAnalytics
  helpers). "Forward" and "back" are computed from that order.
- Every stage change is logged to an events table by a DB trigger, not by the app, so history
  can't be skipped.
- Zero Apollo calls.

PROPOSED / REVISABLE (flag back)
- Stalled = no stage change and next_action_date in the past, OR no stage change for 14+ days.
  The 14 days is a starting value.
- Forecast buckets use expected_close: 0–30, 31–60 and 61–90 days from today. "Weighted" =
  covered_lives × probability and est_value × probability.
- Default probability per stage, overridable per row (starting values): target 0.02,
  contacted 0.05, responded 0.10, meeting 0.20, proposal_pilot 0.40, verbal 0.70,
  contract 0.90, launched 1.0, lost 0.

## Out of scope
- Syncing Apollo deals. An earlier audit found HomeLover isn't using Apollo deals; follow-on
  sales-apollo-deals-v1 if that changes.
- Live import from the Google Sheet. Follow-on sales-analytics-sheets-import-v1, which needs the
  sheet's real columns. v1 uses CSV upload.
- Company intel and research (sales-goals-intel-v1).
- The scorecard and narrative report (separate SPECs).

## Implementation
FIRST: read the existing salesAnalytics components, api/sales/routes.js, and the existing sales_*
migrations. Report the real table naming, tenant column, and route and validation pattern in
5–10 lines, then follow them. This SPEC describes behavior, not an exact diff.

    id, tenant_id, organization text not null, cohort text, org_type text check in

    'target', probability numeric null (null = use the stage default), est_value numeric null,
    owner text, next_action text, next_action_date date, expected_close date,
    expected_launch date, decision_makers text, champion text, objections text,
    competitors text, needed_to_advance text, notes text, is_top boolean default false,
    lost_reason text, source text check in ('manual','csv') default 'manual',
    archived_at, created_at, updated_at
  sales_opportunity_events
    id, tenant_id, opportunity_id, event_type ('created'|'stage_change'|'archived'),
    from_stage, to_stage, changed_at default now()
    An AFTER INSERT/UPDATE trigger on sales_opportunities writes these rows.

### Stage 2 — API
List (filters: stage, cohort, owner, is_top, include_archived), create, update, archive, and
CSV import. Validation matches the existing PUT behavior (unknown field → 400, bad enum → 400,
bogus id → 404).
CSV import: header-mapped (case-insensitive) and validated row by row. Return
{ inserted, updated, errors:[{row, reason}] }. Upsert by (tenant_id, lower(organization)).
Provide a downloadable template CSV with all columns. Movement endpoint: for a [from, to] window,

### Stage 3 — UI (new widgets in the Sales Analytics widget registry, after the KPI tiles)

  Forecast 30/60/90: three columns with count, covered lives, weighted lives and weighted value,
    plus the org names in each bucket.
  Top Opportunities: is_top rows as cards showing decision makers, champion, objections,
    competitors, next step, and what's needed to advance.
  Empty state: "No opportunities yet — add one or import a CSV" with a template link.
  The existing Sequence Leaderboard must use the same table column-alignment approach (see
  FIX sales-leaderboard-alignment-v1) if that has shipped. Otherwise use a single shared column
  definition from the start.

### Stage 4 — Export
CSV per widget, and a "Pipeline" page in the PDF after the existing widgets. The final ordering
is handled by sales-weekly-report-v1.

FIX — prospector-basic-auth-v1

## Status
Source: a read-only access check run by Claude Code on 2026-10-01 before sales-hot-prospects-v1.
Findings (live-verified): server.js has no auth middleware. All /api/* routes are open to anyone
who has the Render URL. One unauthenticated GET /api/sales/<HomeLover id>/runs returned HTTP 200
with real data. Write routes are also open: sync (spends Apollo calls), sequence tags, and
pipeline create/update/archive/CSV import. Business IDs are publicly listable through the anon
key. ProspectorGate is a localStorage flag the server never sees. The Anthropic proxy and the
other /api/* routes are open the same way.
Decision (Jack): Option A, Basic Auth on the WHOLE app. This blocks sales-hot-prospects-v1, which
will store prospect names, titles and phones.

## Problem
Anyone with the URL can read and change HomeLover sales data, trigger Apollo syncs, and use the
Anthropic proxy (running up the API bill).

## Design decision
DECIDED
- One Express middleware near the top of server.js, before static files and all routes, that
  requires `Authorization: Basic` matching the env vars BASIC_AUTH_USER and BASIC_AUTH_PASS.
  Compare with crypto.timingSafeEqual on equal-length buffers (hash both sides first, so a
  length mismatch can't leak timing). On failure, return 401 with
  `WWW-Authenticate: Basic realm="Prospector"`.
- FAIL CLOSED: if either env var is missing in production, every request gets 503 "Auth not
  configured". It must never silently open up. Locally, NODE_ENV !== 'production' may skip auth
  only if BASIC_AUTH_DISABLED_LOCAL=1 is set explicitly.
- Exempt paths, exact matches only: /api/zoom/webhook. Report any other machine-to-machine
  inbound route you find (webhooks or callbacks a third party calls server-to-server) and STOP
  for Jack's OK before exempting it. Do not exempt anything on your own.
- In-process cron is unaffected (it makes no HTTP request). Confirm this.
- Never log the Authorization header or the credentials.

PROPOSED / REVISABLE
- Gmail and SFDC OAuth callbacks are browser redirects to the same origin and should carry the
  stored credentials. Verify with a real click-through after deploy. If one breaks, report it;
  do not exempt it without Jack's OK.

## Out of scope (named follow-ons)
- AUDIT prospector-supabase-anon-exposure-v1: 18 tables are readable directly from Supabase with
  the public anon key (RLS USING true), including HomeLover accounts data. Basic Auth does NOT
  fix this. It needs its own audit and then FIXes with real RLS policies.
- Per-user logins and seats (Cyrus etc.).
- Removing ProspectorGate. Leave it in place.

## Implementation
1. Add the middleware and the exemption list in one small module (e.g. api/basicAuth.js), and
   mount it in server.js.
2. Before deploying, tell Jack EXACTLY what to set in Render: Dashboard → the Prospector service
   → Environment → add BASIC_AUTH_USER and BASIC_AUTH_PASS (he picks them; suggest 20+ random
   characters for the password). Wait for Jack to confirm they're set BEFORE pushing, because
   fail-closed would otherwise lock the site at deploy.
3. Commit, push, and confirm the Render deploy.

## Verification (against the live deploy)
- No credentials → 401 on: / (app shell), GET /api/sales/<id>/runs, and one Anthropic proxy route.
- Wrong password → 401. Right credentials → 200 on the same routes.
- POST to /api/zoom/webhook with no credentials → NOT 401 (it reaches its own handler).
- The next scheduled 6am cron sync still runs. Check sales_sync_runs for trigger='cron' the
  following morning and report it.
- Jack opens the site in a fresh browser window: the password prompt appears, he logs in, and
  Sales Analytics works normally, including Sync now, the pipeline edit and the PDF export (bar 5).
- Credentials never appear in logs (grep the Render logs after the tests).

## Commit instructions
Single commit referencing prospector-basic-auth-v1. Push ONLY after Jack confirms the Render env
vars are set. Then stop and report.

SPEC — sales-hot-prospects-v1

## Status
Source: Jack in chat, 2026-09-30. Jack and Cyrus (freelance sales) want to meet DAILY to go over
"hot prospects": who opened, clicked or replied. They decide who owns each person and what to
do next ("here's what we can send them", "call them"). Jack: "my overlay is gonna be much cooler
and more flexible than base Apollo."
DEPENDS ON: sales-pipeline-v1 (the "Add to pipeline" action). Runs right after it.
This is the daily-use screen. The scorecard and weekly report are the weekly-use screens.

## Problem
1. Apollo shows engagement per sequence. There's no single daily list of "who engaged since
   yesterday, who owns them, and what we're doing about it."
2. Decisions made in the Jack/Cyrus huddle (owner, next step, what to send) live nowhere, so
   follow-ups slip.
3. Open signals are noisy (security scanners auto-open emails), so the list must weight clicks
   and replies above opens and be transparent about why someone is "hot".

## Design decision

DECIDED
- New tab inside Sales Analytics: "Daily Huddle", in the design-v1 style (tokens and mockup look).
- Signal sources: Apollo per-email activity (opens, clicks, replies) for the last 14 days,
  pulled by the existing daily sync plus "Sync now". Only fields confirmed in Stage 1 are used.
  Never estimate.
- Heat score: transparent and shown on hover as "why hot". Starting weights, defined in ONE
  config file (REVISABLE):
    replied +100 · clicked +40 per distinct click day · opened +5 per distinct open day (max +15)
    · decays 50% after 3 days without a new signal.
  Exclusions: bounced, unsubscribed, and contacts already in pipeline at stage ≥ meeting (those
  show in the pipeline instead).
  "Possible bot open" badge: an open within 60s of delivery with no other signal (REVISABLE;
  only if Stage 1 confirms timestamps exist).
- Each hot-prospect card shows: name, title, company, cohort dot, Audience
  (sales-sequence-motion-v1), sequence and step, signal badges (Replied / Clicked / Opened ×N),
  the last signal as a relative time, heat score, owner, status, next action plus due date,
  notes, and links to "Open in Apollo" and LinkedIn if Apollo has it. Phone appears only if
  Apollo returns one; never invent contact data.
- Owner: Jack | Cyrus | Unassigned. Default comes from the sender mailbox (jack@ → Jack,
  cyrus@ → Cyrus), changeable in one click.
- Status: New → Claimed → Contacted → Booked, or Not now (snooze until a date) or Dead.
- Next action: Call · Email · LinkedIn · Send collateral · Wait, with a due date.
- "Send collateral": picks from a small Collateral library (title, url, type, cohort tags) with
  copy-link and copy-snippet buttons. Seed it EMPTY. Jack adds the real items (e.g. the
  rent-vs-buy video and the blog post).
- "Add to pipeline": creates a sales_opportunities row (organization = contact's company,
  stage = 'responded', org_type from Audience, owner) and marks the card "In pipeline".
- Huddle layout (top to bottom):
    Header: "Daily Huddle · <date>" · last synced · Sync now
    1. Due today / overdue (anything with a next-action date ≤ today)
    2. New since last huddle (status New, sorted by heat)
    3. In progress, grouped by owner (Jack | Cyrus columns)
    4. Done since last huddle (Contacted/Booked yesterday or today, as a collapsed recap)
  A "Start huddle" button stamps huddle_at, which defines "since last huddle".
- Every change (owner, status, next action, notes) is logged with who and when.
- Export: "Huddle sheet" CSV, and a print view (light theme) listing the day's assignments by

Every write Scout has goes: typed command or a row's button -> POST /plan (actions.js:89, no record write) -> the
confirm card -> POST /act (actions.js:153) -> the module's existing writer -> POST /undo within 15 s (actions.js:177).

undoFlow · applyPerson / undoPersonEvent · updateProspectRoute · todoOn · applyTodo / undoCreate / undoTodoEvent ·
createWeekGoalRoute / updateWeekGoalRoute · rejectTarget · deprioritize · composeEmail (a draft, never a send).
The 18 verbs (scoutVerbs.js:587): assign_owner :490 · assign :128 · not_fit :235 · contacted :194 · task_finish
:438 · task_done :418 · task_due :421 · task_drop :419 · work :427 (opens a panel) · draft :322 · bundle :349
(clipboard) · snooze :272 · five_add :536 · five_remove :560 · reply_todos :471 · add_task :364 · link_named :512 ·
copy :576 (Copy for Claude, no write).
Refused by rule (actions.js:25-30): send / reply / forward, delete, a stage move or a client, any Apollo write.
Viewers are refused at /plan (actions.js:95). A batch is at most 25 rows (:18).

None of this reads the retrieval. /plan takes the rows of the answer on screen from the client (actions.js:103-104)
and resolves the command against them (resolveTargets :56). If retrieval changed, the only contract to keep is the
item shape Scout returns for a row: entity, id, title, company, row (retrieve.js:340) and the row's verb, which
comes from Today's own read (scoutIntents.js:365), not from the model.

Is the model's text parsed for actions anywhere? No write is. Checked by reading ask.js, actions.js, scoutVerbs.js and
by grep of the client's action files for the answer text (useScoutActions.js, scoutActions.js: no use of answer_md or
summary). The model's text is parsed in three places, all for display:
 - [rN] labels -> which records become rows (ask.js:53, :66-80); an unknown label is dropped
 - "@@ n" blocks -> which rows sit in which section (ask.js:131, :144-157)
 - the "+ n more (in the table):" line (ask.js:65, :104)
So the model picks which rows are SHOWN, and each shown row carries verb buttons a person may click. It cannot
cite a record the server did not read. The "assign it?" offer is built by the server from the owner field
(ask.js:213-218), not from the text.
Two things to hold on to in a rebuild:
 - /plan is "no write" for records, but the draft verb with inline: true makes a model call with composeEmail's own
   cap and usage row (scoutVerbs.js:322-345; the bar always sends inline, useScoutActions.js:77). It is outside the
   40-ask cap and is reached by any line that starts with "write" or "draft" (F5).
 - the commands are matched on what the user typed (scoutActions.js:12, actions.js:63), never on what the model
   wrote. A model that plans reads must stay on the read side of that line.

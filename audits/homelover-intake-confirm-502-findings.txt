============================================================
Q5 — APP-SERVER 502 vs RENDER PROXY/INFRA 502
============================================================
Strong evidence this is a proxy/infra-layer 502, not an app-level one.

intake-confirm.js:81-83 wraps its entire body in try/catch and always
returns JSON on failure: `catch (e) { return res.status(500).json({
error: e.message }); }`. A normal thrown error - including
callAnthropic's own AbortSignal.timeout() firing at 90s
(shared.js:445, isLight ? 90000 : 180000) - is a regular JS error that
this catch block would receive and turn into a clean JSON 500, not an
HTML 502. The reported symptom (HTML DOCTYPE page, "Unexpected token
'<'") is the classic signature of a response that never reached this
handler's own res.json() call at all - Render's proxy/load balancer
returning its own generic error page because the upstream connection
was cut, the worker didn't respond in time, or the worker
crashed/restarted mid-request.

Compounding real finding: intake-confirm.js declares `config.maxDuration
= 30` (30 seconds) while the function it calls can legitimately run up
to 90 seconds (generateProfile's own internal AbortSignal timeout for
light depth) - and real live timing today (Q4) shows normal calls
already landing in the 27-68s range, some already past the declared 30s
figure. Whether `config.maxDuration` is actually enforced anywhere in
this app's real Express/Render runtime (CLAUDE.md confirms api/ files
run inside a real persistent server.js process, not literal Vercel
serverless functions, so this field may be inert/vestigial) could not
be confirmed without Render log/config access (see Q3) - but even if
it's inert, the real 27-68s call durations measured live today are
independently long enough to be a real, plausible target for whatever
Render's actual platform-level request timeout is.

============================================================
ROOT CAUSE THEORY
============================================================
HIGH confidence on mechanism, MEDIUM confidence on exact numeric
threshold (blocked by no Render log access):

This is a proxy/infra-level timeout, not an application bug and not a
content-specific parsing/logic failure. fileCompanyIntel ->
generateProfile's real, live, measured latency (27-68s across 3 real
calls today, 2 different businesses) already sits close to whatever
Render's real request-timeout ceiling is. On the day this was
reported, a real Anthropic call for HomeLover's "File as company
intel" action likely ran slow enough (Anthropic-side latency, HomeLover's
growing intel log making the call itself take longer, or both) to
exceed that ceiling, causing Render's proxy to cut the connection and
return its own generic 502 HTML page before Express's own JSON error
path (which would have fired cleanly on any ordinary JS error) ever got
the chance to run.

NOT ruled out but LOWER confidence: a genuine app-level crash (OOM,
uncaught async exception outside the try/catch, e.g. in code that runs
during Express's response-serialization step) causing a real worker
restart. Real Render log access would be needed to distinguish this
from the timeout theory definitively - flagged, not resolved, per Q3.

This is real, load-bearing evidence that this route's latency profile
- not this session's earlier code changes specifically - is the actual
risk surface. 6dafc88 and the outreach-examples commits are confirmed
NOT to have introduced new failure modes here; they're just sharing
the same pre-existing generateProfile call that has apparently always
run this slow (or slower, pre-6dafc88, when the same call could
truncate at 2048 tokens and get retried/reasoned-over via adaptive
thinking - itself a candidate for EVEN SLOWER pre-fix latency, though
that's speculative without pre-fix timing data, which wasn't
collected).
